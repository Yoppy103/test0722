# スマレジ / Bカート API 技術検証（PoC）

会員別価格（掛け率）を外部から API で更新できるかを検証するためのスクリプト一式。
**本番構築用ではなく、「できるかどうか」を見極めるための検証コード。**

## 検証する3点

1. スマレジ / Bカートの無料トライアル環境に対し、外部から API で会員別価格（掛け率）を更新できるか
2. 更新1件あたりの所要時間の計測
3. 更新結果が会員のログイン画面に反映されることの確認

## いま確実に言えること / 実機確認が必要なこと

| 項目 | 状態 |
|---|---|
| Bカートのレート制限は 300req/300秒（超過で300秒ロック） | **確定**（公開情報） |
| スマレジの価格区分: 1=商品単価, 2=会員価格, 3=原価, 4=商品単価詳細, 5=会員価格詳細 | **確定**（公開情報） |
| Bカートに「価格グループ別の掛け率」「会員ID別の単価」機能がある | **確定**（公開情報） |
| **スマレジで会員（顧客グループ）ごとに異なる価格を持てるか** | **未確定 ★最重要** |
| 各エンドポイントの正確なパス・リクエストボディ | **未確定** |
| 一括更新APIの有無 | **未確定**（有無で所要時間が2桁変わる） |

未確定項目は `config/endpoints.yaml` に `confirmed: false` として明示してあり、
`00_probe_capabilities.py` が実機に問い合わせて判定する。
詳細は [`docs/01_API調査メモ.md`](docs/01_API調査メモ.md) を参照。

## 使い方

### 1. まずモックで動作確認する（トライアル環境が不要）

トライアル環境の払い出し前でも、スクリプト一式を通しで動かせる。

```bash
./scripts/run_all_mock.sh
```

内蔵のモックサーバ（`mock/mock_server.py`）がスマレジ / Bカート の API と
会員ログイン画面を模擬し、`out/mock/REPORT.md` まで一気に生成する。

**失敗シナリオの再現**（スマレジが顧客グループ別価格に対応していない場合）:

```bash
MOCK_SMAREGI_GROUP_PRICE=off MOCK_SMAREGI_BULK=off ./scripts/run_all_mock.sh
```

制約を検知して早期に中断し、`--no-group` での切り分けを促す動作を確認できる。

### 2. トライアル環境に対して実行する

`--mock` を外すだけで実環境に向く。**必ず 00 から順に実行すること。**

```bash
# ① まず「何ができるAPIなのか」を実機に問い合わせる（★ここが最重要）
python3 scripts/00_probe_capabilities.py

# ② ダミーデータ投入（商品20点・会員3社）
python3 scripts/10_seed_smaregi.py
python3 scripts/11_seed_bcart.py

# ③ 会員別価格を更新しつつ所要時間を計測
python3 scripts/20_update_prices_smaregi.py
python3 scripts/21_update_prices_bcart.py

# ④ 反映確認（API再取得 + 会員ログイン画面）
python3 scripts/30_verify_reflection.py --shop-url https://xxxxx.bcart.jp

# ⑤ 結果を集約してレポート生成
python3 scripts/40_make_report.py
```

> **`00_probe_capabilities.py` を最初に実行すること。**
> ここで「スマレジが顧客グループ別価格に対応していない」と判明した場合、
> 以降の進め方が変わる（[`docs/01_API調査メモ.md`](docs/01_API調査メモ.md) の代替案を参照）。

### よく使うオプション

| オプション | 用途 |
|---|---|
| `--mock URL` | 接続先をモックサーバに差し替える |
| `-v` | 全リクエストを逐次表示（デバッグ用） |
| `--out DIR` | 出力先を変更（実行ごとに分けると比較しやすい） |
| `--no-group` | スマレジで `customerGroupId` を送らない（顧客グループ別価格が使えない環境用） |
| `--repeat N` | 計測を N 回繰り返してサンプル数を増やす |
| `--mode stage\|item` | Bカートの更新経路を選ぶ（掛け率 / 個別単価） |
| `--skip-screen` | 画面確認を省略し API 照合のみ実施 |

## 生成物

| ファイル | 内容 |
|---|---|
| `out/REPORT.md` | 検証結果の自動集計レポート（納品物のベース） |
| `out/probe_result.md` | API でできること / できないことの一覧 |
| `out/*timings.csv` | 全APIコールの所要時間の生データ |
| `out/verification_result.md` | 反映確認の照合結果（期待値 vs 実測値） |
| `out/api_trace.jsonl` | 全リクエスト / レスポンスのログ（資格情報はマスク済み） |
| `out/screen_*.html` | 会員ログイン後の商品一覧HTML（画面証跡） |

`out/` は `.gitignore` 済み。検証結果には環境固有の情報が含まれうるため、
リポジトリにコミットする前に内容を確認すること。

## ディレクトリ構成

```
config/endpoints.yaml   エンドポイント定義（confirmed フラグで確度を明示）
src/common/             設定・HTTP（レート制限/リトライ/計測）・ダミーデータ・レポート
src/smaregi/client.py   スマレジAPIクライアント
src/bcart/client.py     BカートAPIクライアント
scripts/00〜40          検証スクリプト（番号順に実行）
mock/mock_server.py     両API + 会員ログイン画面のモック
docs/                   検証計画・API調査メモ・報告書テンプレート・制約事項
```

## 設計上のポイント

- **エンドポイントは設定ファイルに外出し**。実機で仕様が判明したら
  `config/endpoints.yaml` を直すだけでよく、コードは触らない
- **レート制限は既定で安全側**（Bカートは 1req/秒）。300秒ロックを踏むと
  検証が丸ごと止まるため、速度より安全性を優先している
- **待機時間は計測から除外**。レート制限やリトライの待ちを混ぜると
  「1件あたりの所要時間」が実態より悪く見えてしまう
- **通信ログの資格情報は自動マスク**。トレースをそのまま納品物にできる
- **反映確認は2段階**（API再取得 + 画面）。キャッシュやバッチ反映の
  ズレは画面でしか検出できない
