# スマレジ / Bカート API 技術検証（PoC）検証計画

## 1. 目的

本番構築ではなく、**「できるかどうか」の見極め**を目的とする。
以下の3点について、実機（無料トライアル環境）で事実を確認する。

| # | 検証項目 | 判定基準（合格ライン） |
|---|---|---|
| 1 | 外部から API で会員別価格（掛け率）を更新できるか | 商品20点 × 会員3社 の会員別価格が API 経由で設定でき、GET で設定値が読み戻せる |
| 2 | 更新1件あたりの所要時間 | 60件の更新について 平均 / p50 / p95 / 最大 を数値で提示できる |
| 3 | 更新結果が会員のログイン画面に反映されるか | 会員3社それぞれでログインし、20商品すべての表示価格が期待値と一致する |

## 2. スコープ

### 対象に含むもの
- スマレジ・プラットフォームAPI 経由の商品価格 / 会員価格の更新
- Bカート API 経由の 価格グループ掛け率 / 会員ID別単価 の更新
- 更新〜画面反映までの確認と所要時間の計測
- ダミーデータ（商品20点・会員3社）での実施

### 対象に含まないもの（本番構築時に別途必要）
- 実データの移行、マスタ整備
- スマレジ ⇔ Bカート 間の常時同期（バッチ / Webhook）設計と実装
- エラー時のリトライ運用、監視、アラート
- 権限設計、監査ログ、複数店舗・複数拠点対応
- 性能要件を満たすためのチューニング（本 PoC の計測は環境依存の参考値）

## 3. 前提条件

- 環境は依頼元が用意した**無料トライアル**を使用する
- 実データは使わず、**ダミーデータのみ**で実施する
- 商品20点・会員3社の**小規模**構成
- API 利用に必要なアプリ登録・スコープ付与・APIキー払い出しは、
  検証開始前に依頼元側で完了していること（下記「事前準備」参照）

### 事前準備（依頼元にご対応いただく項目）

| 項目 | 内容 | 理由 |
|---|---|---|
| スマレジ 契約ID | 管理画面から取得 | API のパスに含まれる |
| スマレジ アプリ登録 | client_id / client_secret の払い出し | OAuth 認証に必要 |
| スマレジ スコープ | `pos.products:read/write`, `pos.customers:read/write`, `pos.stores:read` | 権限不足だと 403 になる |
| Bカート API 有効化 | API 利用申請・client_id / client_secret | 契約プランにより API が使えない場合がある |
| Bカート 価格グループ | 3つ作成（会員3社に対応） | 掛け率設定の器。管理画面での作成が前提の可能性あり |
| 会員ログイン情報 | 検証用会員3社のログインID / パスワード | 検証項目3（画面確認）に必須 |

> **注意**: Bカートは契約プランによって API 利用可否・価格グループ数の上限が異なる。
> トライアルで API が使えない場合、検証項目1・2は実施できない。着手前に必ず確認する。

## 4. 進め方（2週間想定）

| 期間 | 作業 | 成果物 |
|---|---|---|
| 1〜2日目 | 環境受領、疎通確認、API 仕様の実機確認 (`00_probe_capabilities.py`) | 能力調査結果 (`probe_result.md`) |
| 3〜4日目 | ダミーデータ投入 (`10_`, `11_`) | 投入済みデータ、ID対応表 |
| 5〜7日目 | 会員別価格更新 + 所要時間計測 (`20_`, `21_`) | 計測CSV、集計Markdown |
| 8〜9日目 | 会員ログイン画面での反映確認 (`30_`) | 照合結果、画面HTML証跡 |
| 10〜12日目 | 追加検証（制限値の実測、失敗パターン、リトライ挙動） | 制約事項一覧 |
| 13〜14日目 | 報告書作成、スクリプト整理、引き渡し | 検証結果報告書、スクリプト一式 |

## 5. 計測方法の定義

「所要時間」は解釈の幅が大きいため、次のとおり定義する。報告時は必ず定義を併記する。

- **計測対象**: HTTP リクエスト送信 〜 レスポンス受信完了までの実時間
- **除外するもの**: レート制限による意図的な待機、リトライの待機時間
  （これらは別項目として合計値を併記する）
- **統計値**: 最小 / 平均 / p50 / p95 / 最大。平均だけでは外れ値が隠れるため p95 を重視する
- **「1件」の定義**: 経路によって意味が異なるため、下表を必ず添える

| 経路 | 「1件」の意味 | 20商品×3会員に要するコール数 |
|---|---|---:|
| スマレジ 会員価格更新 | 商品1点 × 会員1社 | 60 |
| Bカート 価格グループ掛け率 | 会員グループ1つ（全商品に波及） | 3 |
| Bカート 会員ID別 個別単価 | 商品1点 × 会員1社 | 60 |

> この定義差は結論を大きく左右する。「1件30ms」という数字だけが独り歩きすると
> 実運用の見積もりを誤るため、報告書では必ずセットで示す。

## 6. 中止・見直しの判断ポイント

以下に該当した場合は、作業を止めて依頼元に方針を確認する。

- トライアル環境で API が有効化できない
- スマレジで会員（顧客グループ）別の価格を持てないことが判明した
  → 「会員別価格はBカート側に持たせる」構成に切り替えるかの判断が必要
- レート制限により、想定件数の更新が現実的な時間で完了しない
- 会員ログイン画面への反映がバッチ処理で、リアルタイム性が要件を満たさない
