# API 調査メモ（着手前の整理）

本ファイルは**公開情報の範囲で分かっていること**と、
**実機で確認しないと分からないこと**を分けて記録したもの。
実機確認の結果は `out/probe_result.md` に出力され、確定した内容は
`config/endpoints.yaml` の `confirmed: true` に反映する運用とする。

## 1. スマレジ・プラットフォームAPI

### 分かっていること

| 項目 | 内容 |
|---|---|
| 認証 | OAuth 2.0 Client Credentials Grant（アプリ単位のアクセストークン） |
| トークン発行 | `POST https://id.smaregi.dev/app/{contract_id}/token`（sandbox）<br>`https://id.smaregi.jp/...`（production） |
| API ベース | `https://api.smaregi.dev/{contract_id}/pos`（sandbox） |
| 価格区分 (priceDivision) | 1=商品単価 / 2=会員価格 / 3=原価 / 4=商品単価詳細 / 5=会員価格詳細 |
| 商品価格 | `GET /products/{product_id}/prices` で取得。フィールドは storeId, priceDivision, startDate, endDate, price |

### ★ 最大の未確認点：会員「ごと」の価格を持てるか

スマレジの `priceDivision=2`（会員価格）は、公開情報上
**「店舗 × 商品」に対して1つの値**として読める。つまり
「A社には80%、B社には75%」という**取引先ごとの掛け率**を
スマレジ側に保持できるとは限らない。

`priceDivision=5`（会員価格詳細）または `customerGroupId` フィールドが
顧客グループ別の価格を担えるかどうかが、この PoC の分岐点になる。

`00_probe_capabilities.py` はこれを実機で判定し、次のどちらかを出力する。

- **OK（customerGroupId が受理される）**
  → スマレジ単体で会員別価格を保持できる。当初想定どおり進行。

- **NG（400 等で拒否される）**
  → スマレジ単体では会員別価格を持てない。下記の代替案を検討する。

#### NG だった場合の代替案

| 案 | 内容 | 長所 | 短所 |
|---|---|---|---|
| A | 会員別価格は**Bカート側だけ**に持たせ、スマレジは定価のみ管理 | 実装がシンプル。Bカートは会員別価格が標準機能 | スマレジ側（実店舗）では会員別価格が使えない |
| B | スマレジの顧客ランク / 顧客グループ機能で代替できるか再調査 | スマレジ側でも会員別価格が効く | 機能の存在自体が未確認。グループ数の上限に注意 |
| C | 中間システムで会員別価格を保持し、両システムへ配信 | 両システムの制約を受けにくい | PoC の範囲を超える。本番構築の設計案件になる |

> 検証項目1の答えは、「できる／できない」ではなく
> **「どちらのシステムで会員別価格を持つなら実現できるか」**になる可能性が高い。
> 報告書ではその形で結論を書く。

### その他の未確認点

- 価格更新のメソッドが `POST` か `PATCH` か、upsert（無ければ作成）になるか
- 一括更新 API の有無 — **所要時間の桁が変わる**ため必ず確認する
  （60件を1コールで送れるなら、1件あたりの実質時間は 1/60 になる）
- レート制限の具体値 — 公式に明示された数値を確認できていない。実測する

## 2. Bカート API

### 分かっていること

| 項目 | 内容 |
|---|---|
| 認証 | OAuth 2.0。認可エンドポイントは `https://app.bcart.jp/oauth/authorize` |
| 形式 | REST。GET / PATCH / POST でリソースを取得・更新・登録 |
| **レート制限** | **300秒あたり300回。超過すると300秒間ロックされる** |
| 会員別価格 | 「掛け率適用価格」と「個別設定価格」の2通りが存在する |
| 価格グループ | ゴールド会員 / シルバー会員のようなグループを作り、グループ単位で掛け率・単価を設定できる |
| 会員ID別単価 | 会員ID単位での単価設定機能が存在する |

### レート制限が設計を支配する

**300秒で300回、超過すると300秒ロック** は本 PoC で最も重要な制約。

- 実効レートは **平均 1req/秒** に抑えるのが安全
- 商品20点 × 会員3社 = 60件を個別単価で更新する場合、
  純粋なAPI時間が仮に 1件 100ms でも、**制限順守だと約60秒**かかる
- 商品1,000点 × 会員50社 = 50,000件 なら **約14時間**。
  本番規模では「個別単価を全件APIで流す」設計は成立しない

→ 本番を見据えるなら **価格グループ（掛け率）方式**が現実的。
   グループ数ぶんのコールで済むため、会員が増えてもコール数が増えない。
   この観点は PoC の結論として必ず報告書に含める。

本スクリプトでは `config/endpoints.yaml` の `max_requests_per_sec: 1` で
安全側に制御しており、ロックを踏まないようにしている。

### 未確認点

- トライアルプランで API が利用可能か（**着手前に要確認。ここが NG なら PoC 不成立**）
- トークン取得方式（認可コード / クライアントクレデンシャル）のどちらが払い出されるか
- 各エンドポイントの正確なパスとフィールド名
- 価格グループの掛け率を **API から**更新できるか（管理画面のみの可能性）
- 会員ログイン画面への反映がリアルタイムか、キャッシュ / バッチを挟むか
